## 世界与总览的关系

“世界”指整个横向世界状态，不与“档案”构成两套系统。人物、局势、设定、变量和地图应当是同一世界的不同视图，后台演化向同一世界提交变化；剧情负责沿时间整理已发生的故事。

“世界 → 总览”是只读汇总：对象索引、已确认字段、待处理记录数量与近期变化。它没有独立持久化、写入命令或模型调用。当前 `overview.js` 与管理页共用 service 和 IndexedDB；进入页面时，宿主接入层可以初始化世界及同步已有来源。原“档案”导航已移除，旧 `world-records` 路由兼容转到总览。

“设置 → 世界管理”保留新增、修订、来源处理、交易、分支和备份。这个入口用于维护同一世界，不形成另一个业务世界。旧分类页尚未全部改为内核投影，这一迁移边界不因界面重组而改变。

## 可以做什么

在设置 → 世界管理中登记人物、组织、地点、物品和未分类对象。对象拥有固定 ID、名称、别名及来源绑定，改名不改变身份。剧情中的人物与地图中的同一个人物，在名称或明确别名唯一匹配时绑定同一档案；同一来源的不同键、同名歧义对象不静默合并。

详情分为当前事实、待处理记录、身份来源和变更历史。关系可以用引用其他对象的属性记录；归属、所在地、上级地点使用对象引用。已确认金币使用非负整数。库存通过物品归属查询得到，不再维护另一份可以独立变化的库存数字。

可新增档案、改名、添加状态或非事实记录、确认或忽略来源记录、登记已确定结果的交易。登记交易要求先有买方、卖方、物品、双方已确认金币和卖方的物品归属；同时扣款、收款并转移物品，任一条件失败则全部不提交。这是管理命令，不是自然语言交易识别器，也不替代命运骰子。

## 核心契约

`domain.js` 不依赖宿主 DOM、Tavern 全局变量或存储 API。它接收完整分支状态和命令，返回新状态及提交收据；不修改输入对象。`service.js` 提供绑定检查、来源同步、分支及恢复接口，`storage.js` 实现可替换的持久化适配器。界面仅调用 service。

| 数据 | 本版语义 |
| --- | --- |
| worldId / branchId | 世界身份与当前历史路径 |
| version | 分支提交序号，不是世界时间 |
| entities | 固定身份、类型、名称、别名、来源绑定、当前事实字段 |
| claims | 传闻、认知、计划、推测、创作候选和待确认材料；处理状态另存 |
| sources | 最近已同步的结构化来源快照及其指纹 |
| events | 每次提交的说明、记录时间和完整前后变化 |
| receipts | 命令身份、完整规范化命令、事件与版本 |

每个当前字段保存来源、事件和版本。候选确认后，原候选的性质和原文仍留在历史中；当前字段注明人工确认。后续来源变化不自动覆盖已确认字段，而是产生新的待处理记录。源记录撤回时，尚未确认的候选撤回，既有身份与已确认状态保留。

命令携带世界、分支、预期版本、唯一命令 ID、操作列表及记录时间。同一个 ID、同一内容重试返回已保存收据；同 ID 不同内容报冲突。预期版本不匹配时拒绝提交。每次操作只修改白名单结构，不执行任意脚本或任意路径写入。来源中的代码、HTML、提示词指令都作为数据，不作为执行权限。

## 持久化与分支

首版使用当前浏览器／应用的 `TavernKitchen_WorldArchive` IndexedDB。三个对象仓库分别保存完整分支、当前聊天绑定及分支所属聊天。一次 readwrite 事务同时提交状态、事件、收据与绑定；不同标签页由 IDB 事务串行化，再用版本检查阻止双写。

聊天键以宿主账户 handle 隔离，再使用角色头像文件或群组 ID、聊天 ID 的 JSON 元组，避免仅凭聊天标题或拼接分隔符串档。聊天切换会使当前服务任务失效；实际提交前再次校验绑定。刷新后读取持久化结果，不重放模型或重新执行交易。

历史分支按事件的前后值重建，保留既有对象身份和来源。恢复完整备份也建立新分支；原分支不被覆盖，可在存档管理 → 查看分支中切回。分支列表与选择校验所属聊天，不能选择其他聊天的分支。当前只提供后厨档案分支；宿主编辑历史、swipe 或聊天分支不会自动回退已确认档案，需在档案中选择对应版本。

导出包含全部管理数据、来源与历史，不包含模型接口配置。文件不是面向玩家的脱密包；本版还没有角色知情隔离服务。备份恢复检查格式、引用、顺序、历史连续性以及当前状态与历史重建结果，限制输入为 20 MB。当前存储以完整分支对象为单位，尚未完成长期大世界性能验证；清除应用站点数据会影响该本地档案，应通过导出迁移。

## 旧模块接入

`sources.js` 提供进程内只读来源注册与变更通知。`imports.js` 将已发表的剧情总结和已确认可读的地图数据转换为档案身份与候选记录。先处理剧情明确的别名表，再处理地图人物名。来源指纹相同则不产生新事件。

首次打开当前对话的总览或世界管理时建立世界并同步；已有档案随后响应旧模块数据通知。没有计时器轮询，没有额外 AI 请求，没有每轮全量 AI 判断。手动同步用于重新读取当前已加载来源。未加载或不可读的来源不视为被删除。

地图位置与上级地点使用同一档案实体引用；剧情关系中能明确解析的目标也引用对应人物。普通旧事实没有记录性质标记，统一保留为待确认，不因模型高置信度直接升级为事实。未知对象先归未分类，可手工确定类型。

档案不会回写旧地图和变量，不改变原模块注入，也不接管世界书。下一步接管时需要按字段确定唯一写入权，再让旧页面读取档案投影；不能同时启用两套权威更新。

## 0.2.14 地图写入与页面读取

地图的应用层仍使用原有地图服务和校验，生产存储改为 `world-records/map-store.js`。地图编辑、维护结果、文档管理和清空地图经统一世界命令提交。地图几何保存在世界状态的 `modules.map`，地点描述、上级地点、人物位置与名称采用同一实体身份。它们和事件、收据、当前分支绑定在同一笔 IndexedDB 事务中确认；确认前不发布候选地图。这里统一的是地图及其相关世界字段，尚未将剧情、变量和后台维护合成一次整理。

首次读取当前聊天的地图时，读取旧地图文件，校验后提交一次接管事件。接管后只读取世界中的地图，不再回写或反复导入旧文件；没有删除旧文件。非法旧地图会显示失败，并可通过文档管理显式修复，不能静默替换为空地图。旧文件仍有未确认保存时，先通过原恢复流程处理。

地图页面根据当前世界投影已确认的名称、地点描述、父级地点与人物所在地。普通布局保存以投影后的基线比较变更，不把旧地图值重新覆盖为当前事实。来源歧义继续保留，不自动合并同名对象。接管时撤回旧地图的待确认候选，保留其历史；当前地图不再作为外部来源反复导入候选。其他来源仍走原确认流程，地图编辑的显式保存作为本次地图字段的确认来源。

若世界把人物移到没有唯一地图绑定的地点，页面隐藏旧位置，已保存的绘图记录保留；保存其他几何不会把人物拉回原地。旧场景中的人物图元会移出当前投影，不为新场景猜测坐标。删除绘图对象或清空地图不删除世界实体、既有事实和事件历史。

世界格式升级为 Schema 2，兼容读取 Schema 1。地图快照及其前后变化随导出、恢复和历史分支保存，并参与历史完整性检查。接管前的旧世界历史没有地图几何：从这类历史版本建立的分支保持空地图，不从当前旧文件导入未来布局。宿主聊天回退与后厨分支仍不自动联动。

地图编辑携带当前视图版本；世界提交、账户／聊天切换及分支切换使旧编辑失效。视图版本是运行期校验标记，不等于持久化世界的 `version`；不同分支即使提交序号相同，也不能接受对方的旧编辑。失败保存保留原状态和待恢复命令，重试复用同一命令 ID；如果其他写入已经改变基线，先重新读取再编辑。切换分支会放弃原分支尚未提交的候选。

本次不增加模型调用。现有地图维护使用原配置和触发方式，只有存储落点改变。变量仍由旧执行器管理，更新者尚未获得完整世界全视快照，来源摘要树、知情过滤与正文双轴注入仍按[下一步方向](NEXT-DEVELOPMENT.md)推进。

## 0.2.15 聊天内变量与兼容副本

后厨聊天内变量的存储权威改为世界存档中的 `modules.variables`。它保存变量值、两套规则、楼层处理签名、1.0 快照、State 2.0 执行记录与检查点，以及后厨待执行变量事件队列。世界格式升级为 Schema 3，继续读取 Schema 1、2；地图与变量的快照都参与分支重建和备份完整性检查。全局变量继续由宿主设置管理，不随聊天分支恢复。

首次进入已启用变量功能的聊天，接管当前全部局部变量与已有后厨执行记录；非法旧数据保留原样并显示失败，可通过面板导入合规 JSON 或明确清空后修复。完成接管后不再从宿主副本反复导入；从接管前历史建立的分支使用空变量状态，不导入未来值。

原有 plot-log、State 2.0、后厨 xb 变量指令、`TK_StateV2.applyText`、变量面板与变量脚本提供的 `setVar` 助手进入世界命令。解释器同步计算隔离草稿，草稿中不能等待外部任务；合法结果中的变量值、规则、处理签名、执行记录和检查点在一笔事务中确认。新旧解释器原有的规则校验与单项拒绝语义继续保留。确认前，面板和宿主读取宏只能看到上一次确认值；派生 State 事件在确认后发布。

消息更新绑定原聊天、分支、消息对象、候选和原文；迟到任务或过期表单被拒绝。已确认签名随世界分支保留，切聊天不清空签名，也不因重复结束通知再次执行同一段加减指令。世界分支选择、恢复或重新读取会刷新宿主变量兼容副本。1.0 回退缺少此前楼层快照时明确失败，不能在未来状态上直接重算旧指令。

保存失败保留最后确认值及准备好的命令。变量面板显示错误，并提供“重试保存”和“重新读取”：重试复用同一命令 ID，丢失确认不会再次执行加减；重新读取放弃未确认候选，关闭旧编辑框。失败期间输入保留，成功前不显示“已保存”。另一位写入者已经改变世界时，旧候选不能覆盖新版本。下一次叙事生成前刷新世界变量；存在未恢复失败时停止发送。

宿主 `chatMetadata.variables` 和后厨变量元数据现在是已确认状态的兼容副本，用于原有读取宏和显示。原生写入宏、其他插件直接写宿主变量、用户脚本直接修改宿主对象或执行原生写入命令，未进入本次世界事务；后续刷新以世界状态恢复副本。任意脚本的外部副作用、变量事件队列的执行与剧情保存也没有合成跨模块原子事务。本次未增加模型调用。

本版统一变量的存储与提交，没有猜测任意变量路径对应哪个人物或事实字段。例：变量树里的“主角.金币”与某实体的 `coins` 字段，只有建立显式绑定后才能作为同一事实更新；当前不自动双向同步。此绑定、稳定每轮来源及已执行效果回执是 P1 的剩余任务；完整世界全视读取和一次整理属于 P2。

## 0.2.16 移除旧变量系统

旧变量面板、导航和设置、xb 指令与宏替换、plot-log／State 解释器、规则守卫、独立快照与检查点回退、变量世界适配器、变量事件脚本、模板变量脚本和记忆回退全局挂钩已删除。23 个源码文件与测试专用 jQuery 依赖移除，删除清单见 [removed-variable-files.json](removed-variable-files.json)。源码检查与构建检查同时阻止旧文件、模块图或运行时符号重新进入安装产物。

金币、位置、归属及其他当前状态通过世界内核的实体字段、校验、命令、事件和分支维护。没有新建替代变量 DSL 或变量面板，也不再初始化、读取、写回宿主局部／全局变量。宿主和其他插件自行提供的变量功能由各自维护。

Schema 3 旧世界备份可能含 `modules.variables`。该对象只作为不透明 JSON 随历史、完整备份和分支保留；没有旧解析器、投影、自动执行或正文注入，新世界命令明确拒绝写入这个模块。恢复时仍核对历史前后值和状态一致性。宿主中的旧元数据及变量值没有被清除，也不会再自动导入。

本次未把任意旧变量路径自动转换为人物或世界事实；无法确定归属的原始值继续封存，不能猜测为当前事实。以后确需整理旧数据，应单独明确来源和对应世界字段。下一步开发不再以旧变量绑定为前置条件，直接补每轮来源与执行回执，然后推进全视独立更新。

剧情锚点及向量召回与旧变量执行器独立，继续通过剧情自己的消息来源、事务和失效机制工作。正文完成后的独立总结默认不变。本次不增加模型调用。

## 0.2.17 每轮来源与执行回执

每轮正文在世界 `sources` 中有独立的 `turn:<id>` 记录，内部版本为 1，沿用世界 Schema 3 的来源扩展能力。记录包含稳定消息 ID、候选 ID、内容版本、实际玩家发言及最终正文、范围和指纹、当前／被替换／已删除状态及记忆交付凭据。世界事件保留修改前后值，备份与分支可重建整个来源账本，不在每次新增一楼时重复写入完整目录。

宿主候选的原生时间标记用于对齐后厨自己分配的 ID；不把楼号或 swipe 下标当作持久身份。正文编辑和续写形成新内容版本，候选切换保留不同候选身份；删除未选候选只导致下标变化时，当前来源不失效。只移动楼号而内容与候选未变时保留来源 ID，原位置仍可从世界历史查询。原生标记缺失或重复的导入消息明确标为内容匹配／身份歧义，保留记忆来源，但不能自动执行世界效果。

独立增量总结在发出模型请求前固定来源凭据，手动单楼总结和编辑使用同一入口。凭据随摘要批次通过已有元数据确认流程保存；聊天、候选、原文、宿主输出边界或世界分支变化会使旧任务失效。带精确来源的新摘要批次在正文改写后按原撤销差量回退，再允许重新整理；刷新页面后也能检查。旧摘要没有凭据时保留原有策略，不根据楼号给它补造已确认来源。

世界只消费已发布的确认记忆。若宿主保存确认丢失或世界交付失败，后续同步重新读取凭据补交，不重新调用模型，也不执行世界效果。`turnProgress().memoryThroughFloor` 只表示从开头连续核实的记忆覆盖范围，不能跨过未核对历史或失败缺口，也不代表世界与记忆已完成统一整理。旧历史需要后续明确回补或基线确认。

世界命令可携带 `origin: {sourceId, effectId}`。来源必须仍是当前、身份明确的正文；效果编号由调用脚本保持稳定。同一来源与效果编号即使更换请求 ID，操作相同也只返回原执行回执，操作不同则拒绝。事件和回执同时保存来源、效果编号及操作指纹；读取 `executionReceipts()` 只取得已落账记录。记忆交付从不重放其中的扣款、归属变化或随机结果。仅有文字相似不能证明两个提案是同一个效果，后续更新者必须复用脚本编号或明确引用原回执。

人工编辑仍保留自己的来源，不自动归到最近正文。正文来源失效且已有执行效果时，现有管理入口仍可读取、导出并从效果前建立分支，但叙事读取与新自动效果会停止，要求先核对；不会顺带撤销后来的人工调整。精确依赖修复和自动历史分支协调尚未实现。

这里的世界版本是摘要来源观察时的版本，当前摘要模型仍未读取完整世界。它不是全视更新的完整基线校验或跨库原子事务。下一步 P2 将在此基础上建立全视快照、分层背景读取接口、统一产出及交付恢复；地图和人工命令也不会被事后猜测成某轮模型行动。本版不增加付费请求，不恢复随正文自动总结或旧变量运行时。

## 0.2.18 全视输入与统一提案

常规回复后的独立总结在原有一次 `summary` 模型请求中同时产生 `summary` 和 `worldUpdate`。来源准备后固定世界、分支、世界版本、语义指纹和记忆 JSON 基线；世界内核尚未就绪时不静默退回无世界输入。手动单楼摘要和直接摘要修订保留原有用途，不因编辑文案重新分析世界。

默认以管理员视角完整提供：所有世界实体与字段、各性质和状态的候选、当前来源数据、地图语义与几何、场景时钟、人物认知、计划和未决记录、尚待核对的世界提案，以及本次增量、最近约 3 条 AI 回复所覆盖的原文和现有早期记忆。不按主角、在场度或相关性裁掉远方和幕后信息。实体字段保持位置／归属权威，地图坐标不能反推世界状态。旧变量模块及其原始来源归档不进入模型输入；历史世界日志和旧楼原文账本通过稳定引用追溯，不作为当前状态反复发送。

上下文清单区分完整当前世界和尚未建立的高阶叙事背景：当前仍使用已有增量记忆、事件及批次摘要，`hierarchyAvailable=false`，没有把它们标成章篇总结树。最近原文数量与 200000 字符输入上限是本版实现参数，尚未完成长篇成本调优。先核对完整材料，再核对拼装后的全部模型消息；超限不调用模型、不截断、不推进总结位置。分区读取与自动拆分仍待实现。

`worldUpdate.proposals` 支持已有对象字段、新对象，以及场景／认知／计划记录三种提案。每条须有本次增量的零基楼号和逐字引文；字段与场景记录要核对准确旧值，关联使用稳定 ID。脚本校验结构、事实性质、数值、引用、重复目标和基线。人物认知保留持有人与认知性质，计划、传闻等不会自动变成事实。统一更新中不再用 `storyUpdates` 绕过提案直接改写当前场景或认知。

模型必须确认所提供的全部已执行回执。已绑定本次来源的效果会阻止同轮同字段再次提出扣款、移动或归属变化；未绑定或较早的人工回执只证明已经执行，不能猜测归属本轮。正文与执行结果矛盾时输出带依据的冲突。无变化可输出空提案，但必须提供非空叙事摘要与完整回执核对列表。

摘要、来源凭据、变化提案、冲突及阅读清单一起走宿主元数据确认。只有已发布的确认批次才能原子投影到世界 `sources['update:<requestId>']` 与每轮记忆交付记录；投影不执行提案中的效果，也不把提案自动转成当前事实。确认丢失或世界投影失败时，原批次保留，之后重新对账即可恢复，不再调用模型或重写已保存元数据。

世界管理新增折叠的“世界变化提案”，展示原值、新值、性质、原文依据与冲突，并能定位现有对象。提案仍需人工核对和登记，尚未增加一键批准／自动执行。事实提案不会显示成已经确认的事实。新批次的叙事摘要也用于楼尾区间展示，事件数组为空时仍可阅读摘要。

模型执行期间世界或记忆 JSON 发生变化时拒绝保存。宿主确认保存期间仍可能发生另一次世界写入：此时保留人工状态，将已保存提案标为 `stale`，不作为有效当前变化；原文失效或摘要回退则标为 `retracted`。世界分支切换后不把旧提案交付到新分支，分支仅继承自身历史中已交付的记录。此流程没有冒充跨宿主文件与 IndexedDB 的原子事务。

本版完成全视读取与摘要／变化提案同请求生成，未完成提案自动审批、分区读取、高阶摘要树、独立 L0 场景卡流程合并或自动世界依赖修复。协议要求叙事摘要只整理本次原文，不把管理员资料中的秘密补入叙事记忆；全视快照不直接交给正文。完整的角色知情视图与防旁路泄露仍须在 P4 实现和验收，不能把提示词约束等同于权限过滤。
